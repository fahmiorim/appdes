## 1. Tujuan dan batas

Matriks B2 mencatat 23 relasi tenant-scoped yang parent-nya belum punya unique key. `0005` menutup 1 relasi (inventaris) dan `0006` menutup 6 relasi (bumindes, galeri, lapak, pengaduan, pemilihan). Sisa **16 relasi** belum pernah dipetakan per kolom: belum jelas mana yang bisa langsung dijadikan composite FK tanpa mengubah perilaku, mana yang terhalang semantik `ON DELETE SET NULL`, dan mana yang tidak layak dijadikan composite FK sama sekali.

Laporan ini hanya menjawab tiga hal: (a) kondisi schema aktual tiap relasi, (b) pengelompokan berdasarkan kelayakan, (c) urutan batch berikutnya beserta prasyaratnya. Tidak ada DDL yang dijalankan dan tidak ada data yang dibaca dari database.

## 2. Metode

1. Membaca definisi tabel di `src/db/schema/` untuk seluruh child dan parent pada Matriks B2.
2. Membaca `src/db/migrations/0000_baseline.sql` untuk nama constraint, nullability, dan aturan delete yang benar-benar terpasang.
3. Memeriksa migration `0001`–`0006` untuk unique key `(village_id, id)` yang sudah ada.
4. Menelusuri `src/features/**` untuk memastikan ada/tidaknya jalur hapus parent di aplikasi, karena itu menentukan apakah perubahan aturan delete berisiko regresi.
5. Tidak menjalankan migration, test, atau query ke database mana pun.

## 4. Tiga temuan yang menentukan pembagian batch

### 4.1 Lima relasi CASCADE siap tanpa perubahan perilaku

Baris #1–#5 memenuhi seluruh syarat composite FK yang aman:

- kolom child `NOT NULL` — `SET NULL` tidak terlibat;
- aturan delete tetap `CASCADE`, jadi menghapus parent tetap menghapus child;
- child dan parent sama-sama memiliki `village_id NOT NULL`.

Empat parent (#1, #2, #3, #4) hanya perlu `UNIQUE (village_id, id)` baru. Menambah unique key ini tidak menyentuh data: `id` sudah primary key, sehingga pasangan `(village_id, id)` dijamin unik secara trivially. `kelompok` (#5) sudah punya unique key sejak `0003`, jadi relasi ini bisa langsung ditutup.

Risiko utamanya bukan semantik, melainkan data lama: baris child yang menunjuk parent desa lain akan menggagalkan `ADD CONSTRAINT`. Karena itu preflight orphan + cross-tenant wajib, mengikuti pola `0004`/`0006`.

### 4.2 Sepuluh relasi `SET NULL` terbagi dua, bukan satu

Semua baris #6–#15 memakai `ON DELETE SET NULL` pada kolom nullable. Composite FK tidak bisa mempertahankan `SET NULL` karena `village_id` child `NOT NULL`; MySQL akan mencoba mengosongkan `village_id` juga.

Yang membedakan bukan aturan FK-nya, melainkan **apakah aplikasi benar-benar menghapus parent**:

- **Tanpa jalur hapus** (#8 `berita_kategori`, #15 `jabatan_perangkat`): mengubah FK menjadi composite `RESTRICT`/`NO ACTION` tidak dapat menimbulkan regresi lewat aplikasi, karena tidak ada use case yang menghapus parent tersebut. Perilaku hapus manual/DBA berubah (gagal, bukan mengosongkan), dan itu perlu dicatat.
- **Dengan jalur hapus** (#6, #7, #9–#12, #13, #14): `RESTRICT` akan menggagalkan alur yang sekarang berhasil. Menutup relasi ini membutuhkan perubahan aplikasi — mengosongkan kolom child di transaksi yang sama sebelum menghapus parent — plus test. Itu pekerjaan yang lebih besar daripada migration, dan menyentuh 8 relasi pada 4 modul.

### 4.3 `users.role_id` tidak layak dijadikan composite FK

`users.village_id` nullable (platform user) dan `roles.village_id` juga nullable (role sistem/global). Repository RBAC secara eksplisit mengizinkan user desa memakai role global:

```ts
// src/features/rbac/infrastructure/rbac-repository.ts:59-60
? isNull(roles.villageId)
: or(eq(roles.villageId, villageId), isNull(roles.villageId));
```

Composite FK `(village_id, role_id) → roles(village_id, id)` akan menolak user desa yang memakai role dengan `village_id NULL`, karena pasangan `(3, 5)` tidak ada di parent. Artinya constraint ini **bukan** hardening, melainkan perubahan model otorisasi. Rekomendasi: pertahankan FK single-column + validasi aplikasi (sudah `app-enforced` menurut matriks §8), dan keluarkan relasi ini dari rencana batch B2.

## 5. Usulan batch berikutnya

### Batch 4B — lima relasi CASCADE (dapat dikerjakan sekarang)

**Isi:** baris #1–#5. Satu migration baru `0007_b4b_cascade_relations_composite_fk.sql`.

Urutan DDL per relasi: `ADD UNIQUE (village_id, id)` pada parent → `ADD INDEX (village_id, <kolom>)` pada child → `DROP FOREIGN KEY <lama>` → `ADD CONSTRAINT <child>_<parent>_tenant_fk FOREIGN KEY (village_id, <kolom>) REFERENCES <parent>(village_id, id) ON DELETE CASCADE`.

Usulan nama constraint: `anggota_grup_kontak_kontak_tenant_fk`, `anggota_grup_kontak_grup_tenant_fk`, `ild_incoming_letter_tenant_fk`, `ols_outgoing_letter_tenant_fk`, `kelompok_anggota_kelompok_tenant_fk`.

Prasyarat dan kelengkapan:

1. Preflight read-only untuk 5 relasi: hitung `orphan` (parent tidak ada) dan `cross-tenant` (`p.village_id <> c.village_id`), gagal sebelum DDL bila ada baris.
2. Tambah 5 constraint ke daftar harapan di `src/db/tenant-composite-fk.integration.test.ts` (daftar saat ini eksplisit dan terurut).
3. Test negatif lintas tenant: insert child desa A yang menunjuk parent desa B harus ditolak untuk kelima relasi; test positif memastikan insert sewilayah dan hapus parent tetap meng-cascade child.
4. Tidak ada perubahan kode aplikasi. Perilaku hapus `kontak`, `kontak_grup`, `kelompok`, `incoming_letters`, `outgoing_letters` tidak berubah.
5. Risiko: DDL `ADD UNIQUE` pada tabel parent mengunci singkat; ukuran tabel kecil (master/pivot). Tidak ada backfill.

### Batch 4C-1 — dua relasi `SET NULL` tanpa jalur hapus aplikasi

**Isi:** #8 `berita.kategori_id`, #15 `perangkat_desa.jabatan_id`.

Menambah `UNIQUE (village_id, id)` pada `berita_kategori` dan `jabatan_perangkat`, lalu mengganti FK menjadi composite `RESTRICT`. Tidak ada use case hapus parent saat ini, sehingga tidak ada regresi yang bisa dibuktikan lewat aplikasi. Yang berubah: penghapusan parent manual/DBA akan gagal selama masih dirujuk, alih-alih mengosongkan kolom.

Prasyarat: konfirmasi maintainer bahwa `RESTRICT` diterima untuk dua parent ini, plus test bahwa hapus desa (cascade `villages`) tetap berhasil.

### Batch 4C-2 — delapan relasi `SET NULL` dengan jalur hapus aplikasi

**Isi:** #6 `analisis_kategori`, #7 `polygon`, #9–#12 `letter_classifications`, #13 `inventaris_kategori`, #14 `kelompok_master`.

Setiap parent di grup ini punya use case hapus yang saat ini berhasil dan mengosongkan referensi child. Menutupnya memerlukan, per parent: transaksi yang mengosongkan kolom child lebih dulu, baru menghapus parent; lalu composite FK `RESTRICT`; lalu test alur hapus (kategori yang masih dipakai) dan test negatif lintas tenant.

Karena `letter_classifications` menghidupi 4 child sekaligus, grup ini sebaiknya dipecah lagi per modul agar satu PR tetap terukur:

- **4C-2a:** `letter_classifications` (4 relasi) — modul surat.
- **4C-2b:** `analisis_kategori` + `polygon` + `inventaris_kategori` + `kelompok_master` (4 relasi) — empat modul berbeda, masing-masing satu relasi.

Alternatif yang sah dan lebih murah: pertahankan single-column + validasi application layer seperti keputusan Batch 3 untuk `inventaris_kategori`, lalu catat sebagai risiko terbuka. Pilihan antara `RESTRICT + transaksi` dan `single-column + app guard` adalah keputusan maintainer, bukan keputusan teknis yang bisa diambil di sini.

### Di luar batch: `users.role_id` dan tabel anak tanpa `village_id`

- `users.role_id` — tidak dijadikan composite FK (alasan §4.3). Cukup dicatat bahwa enforcement-nya di application layer.
- `survey_soal`, `survey_responden`, `survey_jawaban`, `pembangunan_dokumentasi` — membutuhkan kolom `village_id` baru + backfill; tetap kandidat batch terpisah berisiko tinggi sesuai matriks §7.

## 8. Risiko dan keterbatasan

1. Pemetaan ini statis. Tidak ada database yang diperiksa, sehingga jumlah baris orphan/cross-tenant di data nyata belum diketahui; preflight Batch 4B tetap wajib.
2. Penelusuran jalur hapus memakai pencarian kode pada repository. Jalur hapus yang dibangun lewat query mentah atau endpoint di luar `src/features` mungkin belum tertangkap.
3. Perilaku hapus desa (`villages` cascade) ketika salah satu child memiliki FK `RESTRICT` ke parent lokal belum diuji di laporan ini; ini prasyarat Batch 4C-1/4C-2.
4. `incoming_letters`/`outgoing_letters` tidak memiliki jalur hapus aplikasi saat ini, tetapi `0006` sudah lebih dulu memakai `CASCADE`; keputusan yang sama dipakai di 4B agar konsisten.

## 9. Kesimpulan dan rekomendasi

Sisa 16 relasi B2 bukan satu pekerjaan homogen. Lima relasi CASCADE dapat ditutup sekarang tanpa risiko perilaku; dua relasi `SET NULL` dapat ditutup bila `RESTRICT` disetujui; delapan relasi `SET NULL` memerlukan transaksi aplikasi dan sebaiknya dipecah per modul; satu relasi (`users.role_id`) sebaiknya tidak dijadikan composite FK sama sekali.

Langkah berikutnya yang direkomendasikan: kerjakan **Batch 4B** sebagai satu migration `0007` + preflight + integration test, lalu minta keputusan maintainer atas `RESTRICT` untuk 4C-1 dan pilihan `RESTRICT + transaksi` vs `app-enforced` untuk 4C-2 sebelum menyentuh delapan relasi tersebut.
